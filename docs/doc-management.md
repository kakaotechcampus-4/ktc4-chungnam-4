## 원칙

### ① 테크스펙 — 저장소가 FR/NFR의 원본

저장소 `docs/테크스펙.md`를 **코드 작성에 필요한 것만** 남겨 경량화합니다 (FR/NFR 표, 데이터 모델, 파이프라인). 배경·시장·일정은 노션에만 둡니다 — 코드 작업의 기준으로 참조하지 않습니다.

**순서: 회의 후 저장소를 먼저 고치고 → 노션에 반영합니다.** 노션을 먼저 고치지 않습니다. 순서가 깨지면 어느 게 최신인지 알 수 없습니다.

### ② CLAUDE.md — 코드와 직접 연관되므로 가장 중요

회의가 끝나면 즉시 고칩니다. 계층으로 나눠 필요한 사람에게만 붙게 합니다.

변경 등급 2개:
- `[fix]` 문서가 현실과 다른 것 → develop 직접 push + 채널 1줄 공지
- `[rule]` 규칙 자체가 바뀜 → PR + 팀 승인

### ③ 회의 결과는 체크리스트로

**2026-09-13 리뷰 회의에서 이 문서(제안서)가 팀 승인됐습니다.** 함께 정한 운영 방식입니다.

- **협업 미팅은 리더가, 리뷰 미팅은 메이커가** 회의 내용을 정리합니다.
- 정리할 때 **확정된 내용과 확정되지 않은 내용을 구분**하고, 비확정은 "비확정"이라고 명시해 김동건에게 전달합니다. 비확정을 확정처럼 적으면 다음 사람이 그걸 근거로 코드를 씁니다.
- 회의 중 생기는 임시 산출물은 자유롭게 만들어도 됩니다. 정리 대상은 결정 사항입니다.
- 문서 반영은 **Claude로 업데이트 → 팀원에게 고지 → 단체 pull** 순서입니다.
- **회의 일정은 저장소 문서에 적지 않습니다.** 가장 자주 바뀌는 정보라 아무도 갱신하지 않고, 매 세션 컨텍스트만 차지합니다. 일정은 디스코드 공지와 개인 캘린더에 둡니다.
  - 일정이 나오면 Claude에게 **"캘린더 등록 문장 만들어줘"** 라고 요청하세요. 저장소를 고치는 대신, 캘린더 커넥터가 붙은 Claude 채팅에 붙여넣을 문장을 만들어 줍니다 (Claude Code 세션에는 캘린더 도구가 없습니다). 문장에는 캘린더 이름(`아이담-충남대 4팀`)·날짜·시각·소요 시간·반복 여부·시간대(Asia/Seoul)와 **등록 전 확인을 받으라는 지시**를 넣습니다.
  - **날짜와 요일은 반드시 계산합니다** (`date -d 2026-09-15 +%A`). 회의록에 "화요일 21시"만 적히므로, "다음 회차"는 **오늘 이후 가장 가까운 그 요일**입니다. 회의록에 없어서 Claude가 채운 값은 **가정이라고 표시**합니다 (루트 §Claude 작업 규칙).
- 같은 이유로 **자주 바뀌는 값 일반을 문서에 쓰지 않습니다** — 요일, 줄 수, 파일 개수, 진행률. 세어서 알 수 있는 값은 세게 하고, 문서에는 그 값이 지켜야 할 **기준**만 적습니다. 실제로 09-11에 적어둔 파일별 줄 수가 한 주 만에 전부 어긋났습니다.

`docs/open-questions.md` 하나에 모읍니다. 파트별로 노션에 따로 두지 않습니다. 정해지면 취소선, 전부 반영되면 파일을 지웁니다. 파트별 확인이 필요하면 저장소 문서(CLAUDE.md + 테크스펙)를 기준으로 Claude Code에 물어봅니다.

### ④ 결정 이유를 한 줄로

CLAUDE.md가 "무엇"만 적고 "왜"를 안 적으면 두 달 뒤 "이거 왜 이렇게 했지"가 나옵니다. 근거 요구사항 ID를 같이 답니다.

```
- 얼굴 임베딩은 AES 암호화 후 bytea로 저장하고, pgvector를 쓰지 않습니다.
  암호화하면 벡터 간 거리 관계가 깨져 SQL로 유사도를 계산할 수 없기 때문입니다 (NFR-01).
```

**판단에 필요한 "왜"는 본문에, 사람만 볼 경위는 HTML 주석에 씁니다**. 주석은 컨텍스트에 주입되기 전에 제거되므로, 주석에 넣은 이유는 Claude가 보지 못합니다. 위 예시의 "거리 관계가 깨진다"는 Claude가 대안을 제안하지 않으려면 알아야 하므로 본문이고, "09-03 회의에서 되돌림" 같은 경위는 주석이 맞습니다.

**"안 한 선택"도 적습니다.** 코드는 한 일만 보여주고 안 한 일은 보여주지 않습니다. `X를 쓰지 않는다`·`Y 경로를 만들지 않는다`는 코드가 생겨도 문서에 남습니다 — 없으면 다음 사람이 그걸 개선이라 믿고 되돌립니다(pgvector가 실제로 그랬습니다).

**이유는 기본적으로 붙이지 않습니다.** 요구사항 ID는 짧으니 항상 달고, 산문 이유는 **조항만 읽고 "이걸 왜 이렇게 했지?"가 나올 때만** 한 마디 붙입니다 — 그 의문이 곧 되돌리는 PR이 되기 때문입니다. 의문이 안 생기는 조항에 이유를 붙이면 컨텍스트만 먹습니다. 취향·사소한 금지는 아예 적지 않습니다.

### ⑤ 고친 뒤 전파

채널에 1줄 공지 → 그 영역 작업 중이면 "CLAUDE.md 다시 읽어줘" → 하드룰이 바뀌었으면 세션 재시작. **기존 코드는 소급하지 않습니다** (하드룰 위반만 예외).

### ⑥ 우선순위

작업 중 참조 1순위는 CLAUDE.md, 요구사항이 충돌할 때 최종 근거는 테크스펙(FR/NFR)입니다. 하드룰 4개가 전부 NFR에서 파생됐으므로 테크스펙이 근거의 출처입니다.

### ⑦ 한 번 구현하면 그 자체가 명세가 되는 것

API 구조·데이터 모델처럼 코드가 곧 명세가 되는 것은 **매 세션 컨텍스트에 올릴 필요가 없습니다.** 테크스펙이나 도메인 문서에 두고, CLAUDE.md에는 규칙만 남깁니다.

`/doctor` 점검은 체크인된 CLAUDE.md에서 **코드로 알 수 있는 내용**(디렉터리 구조, 의존성 목록, 아키텍처 개요)을 덜어내고 **함정·근거·기본값과 다른 관례**(금지·부재 포함 — ④)는 남기라고 제안합니다. Claude Code v2.1.206 이상이 필요하고, **대화형 `claude` 터미널에서만 실행됩니다** — 데스크톱 앱 세션에서는 쓸 수 없습니다.

### ⑧ 새 문서를 만드는 것이 가장 비싼 선택

만들기 전에 **같은 역할의 문서가 이미 있는지 찾습니다.** 있으면 그걸 고칩니다. `CONTRIBUTING.md`를 만들려다 `backend/README.md` §브랜치와 PR이 이미 그것이었고 이미 낡아 있던 것을 발견했습니다(09/18).

**같은 규칙을 두 곳에 쓰지 않습니다.** 원본을 하나 선언하고 나머지는 링크만 둡니다. 사본이 두 벌이면 한 벌은 반드시 낡습니다 — 갱신을 기억하는 것으로는 막지 못합니다.

## 절차 — 문서를 고쳐야 할 때

### 언제 발동하나

| 상황 | 첫 행동 |
|---|---|
| **회의가 끝났다** | 결정 목록을 만들어 아래 배치표대로 나눠 적고, **`open-questions.md`와 이 문서를 같이 최신화합니다**(§순서 8). **같은 날 합니다** — 미루면 무엇을 정했는지 기억이 갈립니다 |
| **작업 중 문서가 코드·현실과 다른 걸 발견했다** | `[fix]`로 바로 고칩니다 |
| **규칙을 바꾸면 좋겠다는 생각이 들었다** | 문서를 직접 고치지 말고 `open-questions.md`에 **제안으로** 올리고, **디스코드 채널에도 한 줄 올립니다.** 혼자 든 생각은 아직 팀 규칙이 아닙니다 — 다른 사람이 반대할 기회가 있어야 `[rule]` 승인이 형식적이지 않습니다 |
| **멘토 리뷰를 받았다** | 코드 반영은 `refactor/…` 브랜치, 규칙으로 남길 것은 `[rule]` |
| **코드를 짜다 스펙에 근거가 없는 값을 만났다** | 상상해서 채우지 말고 `open-questions.md`에 질문으로 올립니다 (루트 §Claude 작업 규칙) |
| **PR 리뷰에서 문서와 다른 코드가 나왔다** | 문서가 틀린 건지 코드가 틀린 건지 **먼저 정합니다.** 문서가 틀렸으면 `[fix]`, 코드가 틀렸으면 코드를 고칩니다 |
| **한동안 안 봤다** | 문서 간 충돌 점검 + `/doctor` (§원칙 ⑦ 참고) |

### 어디에 적나

| 바뀐 것 | 파일 |
|---|---|
| 요구사항·데이터 모델·파이프라인 | `docs/테크스펙.md` **먼저** |
| 전원이 지킬 규칙, 용어, Git | 루트 `CLAUDE.md` |
| 백엔드/프론트 전반 | `backend/CLAUDE.md` · `frontend/CLAUDE.md` |
| 한 도메인 안의 것 | `backend/domains/<도메인>/CLAUDE.md` |
| 아직 안 정해진 것 | `docs/open-questions.md` |

**가장 좁은 곳에 적습니다.** face에만 해당하는 규칙을 루트에 올리면 전원이 매 세션 그걸 읽습니다.

범위만이 아니라 **언제 필요한 규칙인가**로도 갈립니다. 루트 `CLAUDE.md`는 매 세션 무조건 로드되므로, 특정 작업 시점에만 필요한 것을 여기 두면 나머지 규칙이 묻힙니다.

| 언제 필요한가 | 자리 |
|---|---|
| **항상** — 아무 때나 어길 수 있고 되돌리기 어려움 | 루트 `CLAUDE.md` |
| **특정 작업 시점에만** — 브랜치·커밋·PR·마이그레이션 | `.claude/skills/<name>/SKILL.md` |
| **사람이 판단·합의하는 것** | `backend/README.md`, `.github/pull_request_template.md` |

**스킬로 내릴 때 두 가지를 지킵니다.**

- **루트 `CLAUDE.md`에 "그 스킬을 먼저 호출하라"는 트리거 한 줄을 남깁니다.** 스킬은 호출되지 않으면 안 뜨고, 본문은 컨텍스트가 압축되면 사라집니다. 트리거가 없으면 규약이 실종됩니다.
- **우회 경로가 있는 금지는 스킬에 두지 않습니다.** `develop` 직접 push 금지처럼 제가 스킬을 안 부른 경로에서도 지켜야 하는 것은 루트에 남깁니다. 반드시 막아야 하면 문서가 아니라 훅(`.claude/settings.json`)이 답입니다.

### 순서

1. **스펙이 바뀌었으면 테크스펙 먼저**, 그 다음 CLAUDE.md. 코드가 스펙을 앞서지 않습니다 (루트 §Claude 작업 규칙).
2. **등급을 정합니다** — `[fix]`는 develop 직접 push + 채널 1줄, `[rule]`은 PR + 팀 승인.
3. **이유 한 줄과 요구사항 ID를 답니다** (②④). 판단에 필요한 이유는 본문, 경위는 HTML 주석.
4. **저장소를 고친 뒤 노션에 반영합니다.** 반대로 하지 않습니다 (①).
5. **전파합니다** — 채널 1줄 → 그 영역 작업자는 "CLAUDE.md 다시 읽어줘" → 하드룰이면 세션 재시작 (⑤).
6. **문서 간 참조는 번호가 아니라 제목으로 씁니다** — `backend/CLAUDE.md §코드 스타일`처럼. 절 순서가 바뀌거나 절이 하나 끼어들면 번호 참조는 조용히 다른 곳을 가리킵니다.
7. **참조를 새로 달면 그 자리를 실제로 열어 확인합니다** — 파일이 있는지, 그 절이 있는지, 내용이 지금도 맞는지. 문서를 옮기거나 절을 지우면 가리키던 쪽이 조용히 깨집니다. **Claude가 읽을 수 없는 곳**(노션 링크 등)을 가리킬 때는 `저장소 미반영`이라고 함께 적어, 그 내용을 안다고 가정하지 않게 합니다 (테크스펙 §인터페이스 명세가 그 예시입니다).
8. **회의 내용을 반영했으면 `open-questions.md`와 이 문서도 같이 최신화합니다.** 반영을 끝낸 자리에서 바로 합니다 — 미루면 다음 사람이 낡은 목록을 근거로 코드를 씁니다.
   - `open-questions.md` — 이번에 정해진 항목을 **§결정 기록으로 한 줄로 내리고 반영 위치를 적습니다.** 취소선만 긋고 남겨두면 열린 항목이 다시 묻힙니다. 회의에서 새로 생긴 미정·보류·제안은 §A~§E에 추가합니다.
   - **이 문서** — 새로 합의된 **문서 운영 규칙**만 §원칙·§절차에 넣습니다. **진행 현황은 넣지 않습니다** — 현황의 원본은 `open-questions.md`입니다. 규칙 문서에 현황을 섞으면 규칙이 멀쩡한데도 문서가 틀립니다(09/18에 §남은 일을 걷어낸 이유).

### 하나를 고치면 같이 봐야 하는 것

문서가 계층으로 나뉘어 있어서, 한 곳만 고치면 다른 곳이 조용히 어긋납니다.

| 고친 것 | 같이 볼 것 |
|---|---|
| **용어표** | 그 단어를 쓰는 도메인 문서, 테크스펙의 enum 값 |
| **하드룰(H-n)** | `backend/CLAUDE.md` 필수 테스트 목록, "H-n이 직접 걸리는 도메인" 문서 |
| **데이터 모델** | 소유 도메인 문서의 테이블 표. 마이그레이션 PR이면 테크스펙 ERD도 (`.claude/skills/pr`) |
| **요구사항 ID 신설·등급 변경** | 그 ID를 참조하는 흐름표·도메인 문서의 요구사항 줄 |
| **`open-questions.md`에서 해결 처리** | 테크스펙에 먼저 반영됐는지 (③) |
| **Git 규약(브랜치·커밋·PR)** | 원본은 `.claude/skills/*/SKILL.md` 하나입니다. `backend/README.md` §브랜치와 PR·PR 템플릿·루트 §Git은 **링크와 트리거만** 두고 규약 본문을 옮겨 적지 않습니다 |

## 파일 구조

```
CLAUDE.md                          ← 항상 로드: 하드룰, 용어표, 스킬 트리거, 문서 지도
backend/CLAUDE.md                  ← 백엔드 만질 때
backend/domains/<도메인>/CLAUDE.md   ← 그 도메인 만질 때
frontend/CLAUDE.md                 ← 프론트 만질 때
.claude/skills/<name>/SKILL.md     ← 그 스킬을 호출할 때만 (설명 한 줄만 상시)
docs/
  테크스펙.md                       ← FR/NFR 원본. 필요할 때만 읽음
  open-questions.md                ← 미정 체크리스트
  doc-management.md                ← 이 파일
  README.md                        ← 노션 링크 매핑 (미작성)
backend/README.md                  ← 실행·폴더 구조·담당자. 사람용, 로드되지 않음
.github/pull_request_template.md   ← PR 올릴 때 사람에게 노출
.github/CODEOWNERS                 ← 자동 리뷰어 지정 (팀 자유 영역은 미작성)
```

하위 CLAUDE.md는 **그 폴더의 파일을 읽을 때만** 로드됩니다. 내 도메인 문서는 나한테만 붙고 프론트 작업자한테는 안 붙습니다.

**크기 목표는 파일당 200줄 이하입니다** (Claude Code 공식 권장). 넘으면 어댑턴스가 떨어집니다. 테크스펙은 예외입니다 — 항상 로드되지 않고 필요할 때만 읽히므로 허용합니다. **현재 줄 수는 여기 적지 않습니다** — `wc -l`로 세면 되고, 적어두면 낡습니다 (§원칙 ③).
